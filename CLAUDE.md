# Number Master — project notes

Flutter + Flame clone of "Number Master: Run and Merge" (KAYAC,
`com.kayac.level_up_number`). See README.md for the game rules, project
layout, and publish checklist. This file is implementation/gotcha detail
for whoever (human or Claude) works on this next.

## Architecture in one paragraph

Everything on the track carries a scalar `depth` (distance-to-player) that
decreases at `NumberMasterGame.trackSpeed` every frame; `Projection` (pure
Dart, `lib/game/projection.dart`) turns `depth` + lane into screen
position/scale via `scale = cameraDepth / (depth + cameraDepth)` — the same
scale factor drives Y position, lane X-spread, and render size, which is
what produces the converging-road look without real 3D geometry. Gate/
loose-number/hazard resolution happens at a **distance threshold**
(`TrackEntity.resolveDistance`), not pixel collision — comparing `lane` to
`player.currentLane` at that instant. `WallComponent` is a separate class
(not a `TrackEntity` subclass) since walls are full-width, not lane-scoped.

Levels are generated by `LevelGenerator.generate(level, {seed})` — pure
Dart, deterministic per (level, seed), enforces a fairness invariant (every
row has a non-fatal lane) and wall feasibility (a simulated worst-case
playthrough must be able to afford every wall) *during* generation, with a
sanitizing last-resort fallback (`_sanitizedGenerate`) that can never
return an unbeatable level even if every randomized attempt fails its own
checks. `test/level_generator_test.dart` asserts both invariants across a
spread of levels — always run this after touching the generator, before
ever looking at it rendered.

## Bugs found and fixed during the initial build (2026-08-29)

1. **`_fillNumberRow` currentWorst≤1 edge case**: at the very start of a
   run (player number = 1), a loose number's minimum value (1) is never
   *strictly less than* the player's number, so it's never actually
   absorbable — a "safe" number placement at that point was secretly just
   as fatal as an intentionally-fatal one. Fixed by only placing a "safe"
   number when `currentWorst > 1`, falling back to an empty lane otherwise.
   Caught by `level_generator_test.dart`'s fairness test before this was
   ever rendered — exactly the point of testing the generator standalone.
2. **wallSequence started too early**: the trigger was `_nextRowIndex >=
   rows.length` (all rows *spawned*), not all rows *resolved*. Since a
   row's entities keep `depth == row.distance - traveled` for their entire
   lifetime, the fix is comparing `traveled >= generated.runLength`
   instead — this only caught up with the *last* row actually reaching the
   player, not merely entering the draw window. Found via an actual
   Playwright playthrough (visible in the HUD: "Break through!" appeared
   while normal gate rows were still visibly approaching, and the wall
   count didn't match having passed everything).
3. **`SoundService.init()` could hang the whole app forever**: on some
   browsers, `FlameAudio.createPool()` for a missing/invalid asset doesn't
   reject its Future — it just never completes. Since `main()` originally
   `await`ed `SoundService.instance.init()` before `runApp()`, a single bad
   audio file blocked the entire app from ever rendering (no error, just a
   permanently blank page). Fixed two ways: `main()` now fires sound init
   without awaiting it (`unawaited(...)`), and `init()` itself wraps each
   `createPool` call in `.timeout(Duration(seconds: 5))` so one hung pool
   can't block the rest of the loop either. This is *the* reason
   `SoundService` must never be awaited on the critical startup path.

## Testing this app with a headless browser (Playwright) in a sandboxed environment

Two non-obvious things ate a lot of debugging time here — save the next
session from repeating it:

- **`document.querySelectorAll('canvas')` from the top document will
  always return 0** for a Flutter web app. The actual canvas lives inside
  `<flt-glass-pane>`'s **shadow root**. Query through it:
  ```js
  document.querySelector('flt-glass-pane')?.shadowRoot?.querySelectorAll('canvas').length
  ```
  Every "the app never renders" symptom during this build turned out to be
  this — the app was rendering fine the whole time, the detection script
  was just blind to shadow DOM.
- **`flutter run -d web-server`'s default bootstrap fetches CanvasKit from
  `https://www.gstatic.com/flutter-canvaskit/...`**, unconditionally, even
  though `flutter build web` already bundles the same files locally under
  `build/web/canvaskit/`. If that CDN isn't reachable from wherever the
  browser process actually runs (as opposed to what a plain `curl` from
  the agent's own shell can reach — these can differ in a sandboxed
  environment), the fetch hangs forever with **no console error, no
  pageerror, nothing** — just a permanently blank page. Setting
  `window.flutterConfiguration.canvasKitBaseUrl` in `index.html` does
  **not** work with this Flutter version's bootstrap (it only reads a
  `config` object passed directly into the generated `_flutter.loader.load()`
  call, which the default template never passes). The reliable fix,
  applied purely at the test-harness level (no app source changes needed):
  ```js
  await page.route('https://www.gstatic.com/flutter-canvaskit/**', async (route) => {
    const url = new URL(route.request().url());
    const rest = url.pathname.split('/').filter(Boolean).slice(2).join('/'); // drop /flutter-canvaskit/<rev>/
    const localPath = path.join('<project>/build/web/canvaskit', rest);
    if (fs.existsSync(localPath)) {
      const body = fs.readFileSync(localPath);
      const ext = path.extname(localPath);
      const contentType = ext === '.wasm' ? 'application/wasm' : ext === '.js' ? 'application/javascript' : 'application/octet-stream';
      await route.fulfill({ status: 200, contentType, body });
    } else {
      await route.continue();
    }
  });
  ```
  Run against a `flutter build web --release` + a static file server
  (e.g. `npx http-server`) rather than `flutter run -d web-server`'s DDC
  dev mode — release mode is a single `main.dart.js` instead of ~600+
  individually-loaded dev modules, which is both faster and removes one
  more variable when something isn't rendering.
